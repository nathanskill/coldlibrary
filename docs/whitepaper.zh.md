# 冷冻图书馆协议

**技术白皮书 · v0.1 · 2026-10-05**
状态：草稿。合约已测试，已部署到 Sepolia 测试网（工厂合约 `0x70C3C28db630e3A324db800f6f346e1aFdcE0cA3`，源代码已在 Sourcify 验证）。尚未审计，尚未上主网。

## 1. 摘要

冷冻图书馆是一个开放协议，用来收藏一个人、一个项目留下的东西，并把他们的意志传下去。它由三部分组成：

- **永续展位**（给项目）和**永续铭牌**（给人）。对外只展示主人选定的部分。
- **守馆人**：站在每个展位和铭牌门口的 agent，执行主人设定的考验，把留下的东西交给通过考验的人。
- **冷库**：非托管的智能合约。主人把加密资产放在自己的合约里，由他一个人决定给谁、给多少、什么时候给。

协议从不持有钥匙、原文或资金。没有代币，没有手续费，没有管理员密钥，也没有升级通道。

## 2. 要解决的问题

一个人留下的东西是散的：只有一个维护者的项目、没人知道存在的信、钥匙一丢就跟着消失的钱包。现有的办法要么什么都替你保管（托管方，需要被信任、需要牌照、需要一直不倒闭），要么什么都不管（抽屉里的一张纸）。两者都没法让一个人提前、准确地说清楚：*这些给所有人看；那些只给能证明自己是对的人看；如果我长时间没有音讯，这些资产按这个比例发出去*。

## 3. 原则

1. **主人说了算。** 比例、接收人、开启人、时间和措辞都由主人定；主人还在的时候，随时可以改。
2. **非托管。** 原文在主人的浏览器里上锁；资金放在主人自己的合约里。coldlibrary.com 的运营者既读不了，也动不了、冻结不了。
3. **只转述，不冒充。** 守馆人引用主人的原话并注明日期，从不以主人的口吻说话。
4. **不收租。** 不发币，不收手续费，不按资产抽成，不接受券商、交易所、殡葬、保险机构的赞助。
5. **开放、可带走。** 格式 CC0，代码 Apache-2.0，每个条目都能导出、能打印。"永续"的意思是：只要有人照看，它就一直在，在这里或在别处。

## 4. 架构

```
            ┌──────────────── coldlibrary.com（静态网站 + 很小的接口）─────────────────┐
 主人 ──►   │ 前台：公开层 + 认可层（在浏览器里加密）                                     │
            │ 展位 / 铭牌页面：公开层、守馆人、灯                                         │
            └──────────────────────────────────────────────────────────────────────────┘
                  │ 只有密文                                 │ itemRef
                  ▼                                          ▼
            接口存储（公开层、                     冷库（主人自己的合约，EVM 链）：
            密文、灯）                             资金、继承人、开启人
                  ▲                                          ▲
 访客 ──►   守馆人考验 → 钥匙在访客浏览器里算出 → 信、徽章、指引、点灯资格，
            以及（对继承人）怎样从冷库领取
```

每个条目都有三层：

| 层 | 谁能读 | 放在哪里 | 怎么保护 |
|---|---|---|---|
| 公开层 | 任何人 | 网站 | 主人自己选 |
| 认可层 | 通过守馆人考验的人 | 网站，以密文形式 | AES-256-GCM，钥匙由考验答案推出 |
| 封存层 | 开启人一起，或到约定日期 | 离线，交给保管方 | `age` + SLIP-39 份额（冰芯规范 v0.1） |
| 资产 | 主人指定的继承人 | 冷库合约 | 合约规则 + 继承人自己的钱包 |

## 5. 展位与铭牌

一个条目是一份 JSON 文档（`catalog/items/*.json`），包括：
- `id`（`E-` 是展位，`M-` 是铭牌）、`title`、`subtitle`；
- 公开的 `story`、`facts`、`links`；
- `warden` 块：名字、问候语、问题、密钥派生参数；
- `locked` 块：IV 和密文。

答案永远不公开。为别人立铭牌，需要本人同意；为已经过世的人立，需要直系亲属同意。每份申请都由馆员审核，馆员只能看到公开层。

## 6. 守馆人与考验

**上锁**（在主人的浏览器里，或用 `tools/seal-item.mjs`）：

```
norm(a)   = NFKC(a) → 转小写 → 去掉空白、标点和符号
material  = norm(a1) ‖ U+241E ‖ norm(a2) ‖ …
key       = PBKDF2-HMAC-SHA256(material, salt[16], 210000 次) → 256 位
locked    = AES-256-GCM(key, iv[12], JSON(payload))
payload   = { letter, pointer?, badge?, badge_code?, lamp_token }
```

**解锁**只在访客的浏览器里用 WebCrypto 完成。答错时 GCM 校验失败，守馆人不会说是哪一题错了。服务器从不收到答案、钥匙或原文。

**老实说局限。** 短答案的随机性很低。拿到密文的人可以离线去猜；PBKDF2 能让猜的速度变慢，但对"302"这样的答案挡不住。所以考验只保护信、故事和指引，从不直接保护钱。钱由冷库保护（第 8 节）：只有继承人自己的钱包能领。

**考验的方式**：
- **问题**：已上线。
- **指定名单**（用邮箱验证码确认）：下一步。
- **贡献证明**（比如在某个仓库里被合并的改动）：计划中。
- **接入大模型的守馆人**：正在开发。它能和访客对话，但规矩不变，主人没写下的事它一律不替人决定。

## 7. 灯

payload 里有一个随机的 `lamp_token`，网站只知道它的 SHA-256。通过考验的访客出示这个令牌，才能点一盏灯（可以留 140 字以内的一句话）。所以一盏灯的意思是"一个被认可的人来过"，而不是"有人点了一下"。

## 8. 冷库

冷库（`contracts/src/ColdVault.sol`）由主人通过 `ColdVaultFactory` 自己部署。工厂合约没有所有者，只保留一个公开索引。

### 8.1 参数（由主人设定和修改）

| 参数 | 含义 | 范围 |
|---|---|---|
| `heirs[]` | `(地址, 万分比)`，合计必须正好 10000 | 1–20 位继承人 |
| `keepers[]` | 可以确认失联或叫停的人 | 0–10 位，不能是主人自己 |
| `threshold` | 需要几位确认 | 1 到开启人数（没有开启人时为 0） |
| `heartbeat` | 多久没有报到，开启人才能确认 | 7 天 – 10 年 |
| `vetoWindow` | 凑齐确认后，可以叫停的时间 | 1 – 365 天 |
| `releaseAfter` | 可选：到某个日期自动发放，像时间胶囊 | 0 或未来某个时间 |
| `itemRef` | 关联的展位或铭牌，比如 `coldlibrary:M-000001` | — |

没有开启人的冷库必须设 `releaseAfter`。

### 8.2 状态

```
          主人：存入 / 取回 / 改设置 / 报到（每一个都算报到）
              ┌──────────────┐
              ▼              │
 ┌────────── 正常 ───────────┘
 │   失联超过 heartbeat，threshold 位开启人确认
 │              ▼
 │         确认中 ── 主人报到，或某位开启人叫停 ──► 正常
 │              │ 否决期结束                 （每位开启人在主人两次报到之间只能叫停一次）
 │              ▼
 └ 到达 releaseAfter ─► 已发放 ── 继承人各自领取份额
```

- 主人的每个操作都算报到，并撤销所有进行中的确认。
- 在主人两次报到之间，每位开启人最多叫停一次，所以没有哪一个人能永远卡住发放。
- 重置之后，旧的确认不再算数（`round` 加一）。
- 进入"已发放"之后，主人不能再取回或改设置。

### 8.3 领取

对每种资产 `t`（地址 0 表示链上原生币）：

```
received(t)    = 当前余额(t) + 已领总额(t)
due(t, h)      = received(t) × 份额(h) / 10000
claimable(t,h) = due(t, h) − 已领(t, h)
```

由继承人用自己的地址来领。发放之后才转进来的资产，也按同样的比例分。取整最多留下几 wei 的零头。转账收费型和自动增减余额型代币不支持。

### 8.4 协议做不到的事

除了上面这些规则，没有任何人能动资金：没有管理员，不能暂停，不能升级，没有费用开关。如果继承人弄丢了自己的钥匙，他那一份会一直留在冷库里；主人应该让继承人地址保持最新。如果主人弄丢了自己的钥匙，开启人或约定日期仍然会把资产发给继承人，这正是设计好的兜底。

## 9. 条目与冷库的关联

展位或铭牌可以通过 `itemRef` 关联一个冷库。对继承人，认可层里可以写明：冷库地址、哪条链、他的位置，以及一份白话的领取说明。通过考验，得到的是"怎么领"；只有登记过的钱包"能领"。所以猜中答案，在钱上什么也得不到。

## 10. 安全

| 威胁 | 应对 |
|---|---|
| 服务器被攻破 | 服务器上没有钥匙、原文和资金；最坏情况是页面被改或公开层被删，可以从仓库恢复。 |
| 离线猜考验答案 | 考验后面只放非金钱内容；建议用长一点、私人一点的答案；钱只能由钱包领取。 |
| 开启人串通提前发放 | 需要 threshold 位开启人、加上失联期、再加上否决期；主人一报到就全部撤销。开启人最好彼此不太熟。 |
| 某个开启人永远叫停 | 每位开启人在主人两次报到之间只能叫停一次；`releaseAfter` 兜底。 |
| 主人被胁迫 | 软件管不了；主人随时能取回资金，攻击者也一样。金额要量力而行。 |
| 重入攻击、代币的怪异行为 | 重入锁、先改状态后转账、兼容不规范的 ERC-20 转账；都有测试。 |
| 钓鱼（"请把钥匙发给我们"） | 冷冻图书馆的通知从不带链接，从不索要钥匙、份额、密码、助记词或钱。 |

27 个单元测试和随机测试覆盖了：
- 参数规则；
- 失联、确认人数、叫停次数限制；
- 发放，原生币和 ERC-20 的领取，发放后才到账的资产；
- 按日期发放；
- 重入攻击。

完整流程也在本地链上跑通过。**合约尚未审计。** 独立审计之前，不应放入真钱。

## 11. 法律

冷库是主人用自己的资产使用的工具。它不是法律遗嘱，也不能凌驾于继承法之上；主人应当让自己的法律安排与冷库的设置保持一致。冷冻图书馆不提供投资、法律或税务建议。加密资产相关服务在一些司法辖区受到限制或被禁止，包括中国大陆；在不合法的地方，不提供冷库界面。

## 12. 经济与治理

没有代币，没有手续费，没有投资人。托管费用由创始馆员承担，年度上限公开。合约一经部署就不可更改；改进以新版本发布，主人自己决定是否迁移。馆员维护网站和目录；任何等级都打不开别人的内容，也动不了别人的资金。

## 13. 路线图

1. v0.1：展位、铭牌、问题考验、点灯，冷库在本地测试通过（已完成）。
2. 部署到公开测试网；网站上加冷库页面，用访客自己的钱包，不引入任何第三方脚本。
3. 独立审计；在以太坊主网和一条低手续费的二层网络上线。
4. 指定名单和贡献证明两种考验；同样规矩下的大模型守馆人。
5. 比特币：把带时间锁的描述符钱包（Miniscript）写成指引。
